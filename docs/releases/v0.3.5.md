# Chat Harness v0.3.5

This release improves brownfield adoption and reduces mandatory instruction-loading overhead without changing the validated Workstream/Workbench persistence lifecycle.

## Changed

### Simpler context-loading path

Chat Harness now uses a smaller mandatory instruction path:

```text
AGENTS.md
  -> .chat-harness/WORKSPACE.md
  -> matching Workstream for Work
  -> additional Procedures and authoritative context only as needed
```

Requests are classified as **Answer-only** or **Work** from `AGENTS.md` first. After classification, `WORKSPACE.md` is loaded before domain reasoning or responding for both classes. Answer-only requests remain lightweight and do not create durable Work state unless the request itself requires it.

The previous mandatory `.chat-harness/README.md` Workspace Map layer has been removed from the core scaffold and runtime contract.

### Brownfield setup safety

`chat-harness setup` now detects an existing root `PROJECT_INSTRUCTIONS.md` and preserves it unchanged.

When legacy project instructions are present, setup reports host activation as **migration required** and does not tell the user to replace hosted Project Instructions immediately. This creates a safe review window to migrate still-needed Workspace-specific behavior into `.chat-harness/WORKSPACE.md` before activating the Chat Harness host binding.

Setup still does not move, rename, merge, or semantically reorganize unrelated domain content.

### Specialist seeds

The built-in specialist seeds remain deliberately compact. A small number of high-leverage domain invariants were added:

- **Tech** — separate model capability from harness/tools/context/evaluation configuration.
- **Career** — keep factual truth, positioning, and public-use approval distinct.
- **Tax** — historical records establish historical facts, not current law.
- **Finance** — separate investment return from cashflows, fees, tax, insurance, and timing effects before comparison.
- **Shopping** — verify exact variant/channel and separate dependable economics from uncertain promotional upside.

Detailed domain methodology should continue to live in Workspace-specific Guides, Playbooks, Procedures, repositories, or other canonical sources and be retrieved only when relevant.

## Compatibility

The Workstream/Workbench taxonomy, Markdown contracts, checkpoint semantics, same-purpose artifact reuse, and canonical Workstream reconciliation behavior are unchanged from v0.3.4.

Existing v0.3.4 Workspaces should run:

```bash
chat-harness update
chat-harness setup
chat-harness validate
```

`setup` refreshes the managed `AGENTS.md` to the new startup contract. An existing `.chat-harness/README.md` from an older Workspace is no longer managed or required; it may remain as user-owned content until you choose to remove it.

For existing non-Chat-Harness projects with `PROJECT_INSTRUCTIONS.md`, run normal `chat-harness setup`. The CLI will preserve those instructions and explicitly tell you that host activation is pending Workspace-specific migration review.

## Prompt/context guardrails

- Canonical `AGENTS.md` remains under the project's 7,000-character engineering budget.
- Specialist seeds are regression-tested to remain compact.
- New behavioral evals cover Answer-only Workspace invariants and brownfield host-activation safety.
