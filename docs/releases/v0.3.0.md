# Chat Harness v0.3.0

This release makes durable project persistence explicit, proactive, and mechanically validated.

It is a deliberate Workspace-contract change from v0.2: agents should now persist Work early and consistently instead of relying on vague judgements such as “substantial” or “qualifying”.

## Deterministic Work persistence

- classifies each request as **Answer-only** or **Work**;
- keeps direct, disposable lookups Answer-only while still allowing minimal source retrieval when needed;
- biases ambiguity toward Work so resumable state is created rather than reconstructed later;
- requires Workstreams to be created or resumed before extended research, tool use, or multi-step execution;
- requires agents to save/checkpoint proactively instead of waiting for the user to ask.

## Workbench lifecycle

The Workbench taxonomy is now purpose-driven:

- `0-ideas/` — frame new open-ended objectives;
- `1-research/` — establish evidence for unresolved questions;
- `2-decisions/` — turn evidence, constraints, and tradeoffs into direction;
- `3-plans/` — make a chosen direction executable;
- `4-reviews/` — evaluate an existing artifact, implementation, plan, or outcome.

`2-analysis/` has been renamed to `2-decisions/` because “analysis” was too broad to define a durable artifact reliably.

The categories are trigger-based artifact classes, not a required waterfall.

## Markdown and frontmatter contract

Workstreams and textual Workbench artifacts now have a hard storage contract:

- raw `.md` files only;
- valid YAML frontmatter is mandatory;
- Workstream fields and status values are schema-validated;
- Workbench type must match its folder;
- Workbench status values are `draft`, `approved`, `completed`, or `superseded`;
- `approved` requires explicit authorized approval and is never inferred from silence;
- Workbench artifacts must reference their owning Workstream;
- superseded artifacts must reference their replacement;
- created/updated dates and active Workstream Next actions are validated.

For remote storage, Chat Harness instructions explicitly require Markdown (`text/markdown`) and prohibit silently substituting a native Google Doc or provider-native document when Markdown was required.

## Validation and templates

- adds a Workbench frontmatter JSON schema and validator;
- strengthens Workstream validation;
- rejects non-Markdown files in Workstream/Workbench control state;
- adds canonical templates for idea, research, decision, plan, and review artifacts;
- enforces a 7,500-character CI ceiling for the canonical `AGENTS.md` Project Instructions;
- expands behavioural evals for Answer-only, proactive persistence, lifecycle routing, Markdown/frontmatter, and persistence-failure handling.

## Breaking upgrade note

Existing v0.2 Workspaces are not automatically migrated.

After upgrading, review existing Workspace state before relying on `chat-harness validate`:

- rename existing `.chat-harness/workbench/2-analysis/` to `2-decisions/`;
- update existing Workstream frontmatter to include `type`, `title`, `status`, `created`, and `updated`;
- add required YAML frontmatter and an owning `workstream` reference to existing textual Workbench artifacts;
- rerun `chat-harness setup` to refresh recognized managed `AGENTS.md` files;
- rerun `chat-harness validate` and reconcile any remaining findings.

Chat Harness does not invent Workbench ownership during upgrade when it cannot be inferred safely.

## Upgrade

npm:

```bash
npm install -g chat-harness@latest
chat-harness --version
```

Standalone installer:

```bash
curl -fsSL https://raw.githubusercontent.com/carlosboeing/chat-harness/main/install.sh | sh
```
