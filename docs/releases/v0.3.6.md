# Chat Harness v0.3.6

This patch release hardens hosted Workspace state handling based on real brownfield ChatGPT smoke tests.

## Changed

### More precise Workstream ownership

Chat Harness now reuses an existing Workstream only when the request advances the same objective.

Related domain, strategy, client, or subject matter alone is not enough. Related work should split when it develops a distinct objective and independently resumable Next action.

Before substantive handoff, the harness also re-checks ownership so a subtopic that became independent during execution can be split and its Workbench artifacts repointed to the correct Workstream.

### Freshness-aware source selection

When current Workspace or control-plane state matters, fresh authorized live reads now take precedence over cached or indexed copies when both can access the same underlying source.

Cached/indexed sources remain useful for discovery, but should not be treated as freshness authority when a live connector/app can retrieve current state.

ChatGPT host documentation now explicitly distinguishes:
- Google Drive content attached as a Project source, whose indexed state may lag until refreshed;
- live Google Drive connector/app reads that can retrieve current Drive content on demand.

### Canonical temp-file discipline

`.chat-harness/temp/` is now explicitly staging-only.

Temporary files may support safe remote writes, but user-facing references must resolve to the verified canonical Workstream, Workbench artifact, or domain file. Temp staging files must not be cited or presented as authoritative.

## Regression coverage

Four behavioral regression scenarios were added:
- related-objective Workstream splitting;
- mid-flight Workstream splitting;
- temp staging not leaking as canonical;
- live-source freshness winning over stale indexed state.

The live-source freshness scenario remains a real-host behavioral contract: deterministic repository validation can preserve the expectation, but cannot reproduce hosted indexing freshness by itself.

## Compatibility

No schema, Workstream frontmatter, Workbench taxonomy, Source Policy version, or specialist Workspace contract changed in v0.3.6.

Existing v0.3.5 Workspaces should run:

```bash
chat-harness update
chat-harness setup
chat-harness validate
chat-harness doctor
```

For a recognized Chat-Harness-managed `AGENTS.md`, normal `setup` refreshes that file to the v0.3.6 generic instructions.

Normal `setup` does **not** replace an existing `.chat-harness/WORKSPACE.md` unless `--replace-workspace` is explicitly supplied.

After updating a ChatGPT-hosted Workspace, copy the complete refreshed `AGENTS.md` into Project Instructions and refresh/sync the Project source before rerunning host regression checks.

## Prompt/context guardrails

- Canonical `AGENTS.md` remains under the project's 7,000-character engineering budget.
- Specialist Workspace seeds are unchanged.
- Semantic Workstream ownership remains a host/model behavioral contract rather than a heuristic deterministic CLI validator.
- Source Policy v1 remains focused on privacy/source handling; freshness is not added to the schema in this release.
